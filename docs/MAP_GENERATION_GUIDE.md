# Генерация карты в Roguera 4.0

Гайд описывает текущее состояние алгоритма генерации этажа подземелья — от точки входа до возвращённой структуры комнат, с разбором каждой фазы, иллюстрациями, оценкой сложности и честным анализом сильных и слабых сторон.

Все исходники, на которые ссылается документ, лежат в `src/main/java/kseoni/ch/roguera/map/generator/`.

---

## 1. Что делает алгоритм

Цель: построить **этаж** подземелья — связное множество прямоугольных и составных комнат, соединённых дверями, с прорисованными стенами по периметру.

Этаж — это `Floor` (`map/Floor.java`), который содержит `Map<Integer, Room>`. Каждая `Room` — это плотный набор `Cell`, лежащих в собственной локальной системе координат, плюс смещение `roomLeftTopPosition` в глобальную систему мира.

Алгоритм возвращает либо `Map<Integer, Room>` (готовый этаж), либо `null` (этаж признан невалидным; `Floor` пробует ещё раз).

---

## 2. Терминология

Для каждой аббревиатуры дано определение, плюс короткое пояснение, **зачем** она в этом алгоритме.

### MST — Minimum Spanning Tree (минимальное остовное дерево)

Подмножество рёбер связного взвешенного графа, которое:
- содержит **все** вершины (spanning),
- образует связный подграф,
- не содержит циклов (то есть это дерево),
- имеет минимальную возможную **сумму** весов рёбер.

Дерево на `n` вершинах имеет ровно `n − 1` ребро — это математический факт.

В нашем алгоритме MST строится на графе центров комнат с весом ребра = евклидово расстояние между центрами. MST используется в Phase Three для решения «какие комнаты соединять дверями» — даёт связное подземелье минимальным количеством дверей и без избыточных соединений.

### BFS — Breadth-First Search (обход в ширину)

Алгоритм обхода графа: посетить все вершины «слоями» от стартовой. Стартовую кладём в очередь, на каждом шаге достаём вершину из очереди и кладём всех её непосещённых соседей. Поддерживаем `visited` — множество уже посещённых вершин.

Используется в `MapValidator.isConnected` для проверки связности графа дверей и в `PhaseTwoMergeRooms.clusterizeRooms` для определения, какие комнаты пересекаются и должны быть объединены.

### DSU — Disjoint Set Union (система непересекающихся множеств) / Union-Find

Структура данных, которая поддерживает множество элементов, разделённых на непересекающиеся группы, и две операции:
- `find(x)` — возвращает «представителя» группы, в которой лежит `x`;
- `union(x, y)` — объединяет группы, в которых лежат `x` и `y`.

Используется в Phase Three (алгоритм Краскала для построения MST). Для пары вершин ребра проверяем — `find(a) != find(b)` — если так, ребро можно добавить в MST, потому что соединяет ещё несоединённые компоненты.

### AABB — Axis-Aligned Bounding Box (прямоугольник, выровненный по осям)

Прямоугольник, чьи стороны параллельны осям координат. Для двух AABB пересечение проверяется ровно одним if'ом:
```
a.left < b.right && a.right > b.left && a.top < b.bottom && a.bottom > b.top
```
В алгоритме AABB-проверка пересечения комнат используется в Phase Two как канонический критерий «эти комнаты надо слить».

### Edge cell (граничная клетка комнаты)

Клетка комнаты, которая лежит **на её границе**. В Roguera клетка считается граничной, если:
1. среди её 4 кардинальных соседей (N, E, S, W) есть `null` (за пределами комнаты), **или**
2. среди её 4 диагональных соседей (NE, NW, SE, SW) есть `null` при том, что **оба смежных кардинальных** — cells. Это условие добавляет **вогнутые углы** (клетки, где контур комнаты огибает их по диагонали).

На граничных клетках в Phase Four ставятся стены.

### Cardinal / Diagonal (кардинальные / диагональные направления)

- **Кардинальные** — N, E, S, W (4 шт.).
- **Диагональные** — NE, NW, SE, SW (4 шт.).
- Вместе — 8 направлений вокруг клетки, "роза ветров".

Массивы заданы в `Position.CARDINAL_POSITIONS` и `Position.AROUND_POSITIONS`.

### 4-битная маска edge-клетки

Целое число от 0 до 15, где каждый бит соответствует одному кардинальному направлению:
- `bit 0` (значение 1)  — N (есть edge-сосед сверху)
- `bit 1` (значение 2)  — E (есть edge-сосед справа)
- `bit 2` (значение 4)  — S (есть edge-сосед снизу)
- `bit 3` (значение 8)  — W (есть edge-сосед слева)

Маска однозначно определяет, какой именно глиф стены / угла / T-junction нужно нарисовать в этой клетке. Таблица `mask → glyph` живёт в `TilesUtils.WALL_TILES`.

### Глобальные / локальные координаты

В Roguera каждая комната имеет:
- **локальную** систему — cells хранятся по локальной `Position`, начало координат в верхнем-левом углу комнаты;
- **глобальное смещение** — `roomLeftTopPosition`, точка-якорь в мире.

Конвертация: `global = roomLeftTopPosition + local`. Канонический метод — `Convert.toGlobalPosition(lt, local)`.

## 4. Этап 1 — Phase One: расстановка комнат

### Что делает

`PhaseOneCreateRooms.createRooms(roomCount, worldXBound, worldYBound)`:

1. `roomCount` раз случайно выбирает `(x, y)` в `[0, worldXBound) × [0, worldYBound)`.
2. Для каждой выбранной точки строит комнату: размер случайный 6–15 по каждой оси, cells в локальных координатах от `(0, 0)` до `(width-1, height-1)`.
3. Помещает в HashMap `roomId → Room`.

Никакой проверки на пересечения, на выход за `worldBound` (комната может частично «торчать» за границей) и на минимальное расстояние между комнатами — нет.

### Пример

`worldXBound = 100`, `worldYBound = 50`, `roomCount = 4`:

```
x=0                                        100
y=0  ┌──────────────────────────────────────┐
     │                                      │
     │     ┌───┐                            │
     │     │ A │                            │
     │     └───┘                            │
     │                  ┌────────┐          │
     │                  │   B    │          │
     │                  └────────┘          │
     │     ┌──────┐                         │
     │     │  C   │                         │
     │     └──────┘   ┌─────┐               │
     │                │  D  │               │
     │                └─────┘               │
y=50 └──────────────────────────────────────┘
```

Комнаты разбросаны равномерно. Некоторые могут пересекаться (это ОК, дальше Phase Two с этим разбирается).

### Сложность

| | |
|---|---|
| Время | O(roomCount · max_w · max_h) — на создание cells (`6×6 … 15×15`). |
| Память | то же. |

Для 100 комнат с типичным размером — несколько тысяч cells, доли миллисекунды.

### Преимущества

- Простая, детерминированная при фиксированном seed.
- Не имеет внутренних ограничений на форму world.

### Недостатки

- Может породить комнаты, выходящие за `worldBound` (если `x + width > worldBound`).
- Нет контроля плотности: при большом world и малом `roomCount` комнаты будут разрежены, при обратном — налеплены друг на друга (что Phase Two отчасти лечит).
- Размеры захардкожены `nextInt(5, 15) + 1` — никаких настроек извне.

## 5. Этап 2 — Phase Two: кластеризация и слияние

### Что делает

`PhaseTwoMergeRooms.mergeRooms`:

1. **Кластеризация** — BFS-обход по графу пересечений: две комнаты в одном кластере, если их множества глобальных клеток пересекаются (`hasIntersects`).
2. **Слияние** — для каждого кластера размером ≥ 2 рекурсивный `intersectAndCombine` объединяет все комнаты кластера в одну через попарный `combine`.

### Слияние двух комнат — `combine`

Геометрически правильная процедура (после фиксов в этой ветке):

1. Новый якорь: `newLt = (min(A.lt.x, B.lt.x), min(A.lt.y, B.lt.y))`.
2. Сдвиги: `dxA = A.lt.x − newLt.x`, аналогично `dyA`, `dxB`, `dyB`. Все сдвиги ≥ 0 по построению.
3. Пересчёт локальных координат cells:
   - `A.cell(localA)` → `(localA.x + dxA, localA.y + dyA)` в новом фрейме;
   - `B.cell(localB)` → `(localB.x + dxB, localB.y + dyB)`.
4. Cells второй комнаты добавляются через `putIfAbsent` — пересечения сохраняют клетку первой.
5. Размер новой комнаты — `max(cell.x) + 1` × `max(cell.y) + 1`.

Иллюстрация (A слева, B справа сверху, перекрытие по углу):

```
До слияния (глобальный мир):
y= 0  ········                         
y= 1  ····BBBB···                       
y= 2  AAAABBBB···                       
y= 3  AAAA·······                       
y= 4  AAAA·······                       
y= 5  ···········                       

После слияния (одна комната с newLt в верхнем-левом углу bounding box):
new local frame:
y= 0  ····xxxx                         
y= 1  ····xxxx                         
y= 2  yyyyxxxx                         (пересечение взято из A)
y= 3  yyyy····                         
y= 4  yyyy····                         
```

### Кластеризация — `clusterizeRooms`

```
для каждой непосещённой комнаты:
    создаём пустой кластер
    кладём её в очередь
    пока очередь не пуста:
        текущая = очередь.pop()
        пометить как visited
        добавить в кластер
        для каждой непосещённой r:
            если hasIntersects(текущая, r):
                кладём r в очередь
```

`hasIntersects` сейчас реализован через `Set<Position>.retainAll` — пересечение множеств глобальных клеток. Корректно, но дорого для больших комнат. Канонический эквивалент — AABB-overlap (один if на 4 поля).

### Сложность

Пусть `n = roomCount`, `c` — среднее число cells в комнате.

| | |
|---|---|
| Кластеризация | O(n² · c) — для каждой пары вызывается `hasIntersects` стоимостью O(c). |
| Слияние одного кластера размера `k` | O(k · c) — рекурсивный обход cells. |
| Память | O(n · c). |

Для типичных значений (`n=20`, `c~150`) — миллисекунды.

### Преимущества

- Канонически чистый combine: правильная арифметика сдвигов, иммутабельность позиций, корректный размер.
- Кластеризация через BFS — стандартный подход, легко расширяется.
- Поддерживает любые формы слияния (L, T, +, ступеньки), не только прямоугольники.

### Недостатки

- `hasIntersects` через `Set.retainAll` — O(c) вместо O(1) AABB. На больших комнатах заметно.
- `intersectAndCombine` использует рекурсию вместо `Stream.reduce` — менее читаемо, не выигрывает в производительности.
- В `clusterizeRooms` есть отладочный pollution: цифра кластера ставится в cell `(2, 1)` каждой комнаты в виде Wall — это объект остаётся в финальной карте.
- Cells первой и второй комнат **не копируют содержимое** оригинальных Cell (объекты теряются). На текущем этапе в комнатах ничего важного нет (только отладочные `*` и цифры), но если понадобится — нужно будет тащить контент.

## 6. Этап 3 — Phase Three: соединение комнат через MST

### Что делает

`PhaseThreeConnectClusters.connectRooms`:

1. **Строит MST** методом Краскала.
2. **Для каждого ребра MST** ставит дверь между парой комнат (`placeDoorBetween`).

### Алгоритм Краскала

```
1. Перечисляем все попарные рёбра (n choose 2 шт.):
     edges = { Edge(a, b, dist) для всех пар (a, b) }

2. Сортируем по возрастанию веса.

3. Идём по списку и через DSU добавляем рёбра, если они соединяют
   разные компоненты:
     for edge in sorted(edges):
         if dsu.find(edge.a) != dsu.find(edge.b):
             dsu.union(edge.a, edge.b)
             mst.add(edge)
             if mst.size == n - 1: break
```

После цикла в `mst` лежит ровно `n-1` ребро — гарантированное связное дерево с минимальной суммой весов.

### Иллюстрация MST

Допустим 6 комнат и их попарные расстояния. Полный граф K₆ — 15 рёбер; MST — 5:

```
Полный граф (15 рёбер):       MST (5 рёбер):
                              
   A───B───C                     A   B───C
   │  /│\  │                         │   │
   │ / │ \ │                         │   │
   │/  │  \│                         │   │
   D───E───F                     D───E   F
                              
все соединены со всеми       одна цепочка через все вершины
```

Сумма весов MST минимальна — алгоритм всегда выбирает кратчайшие связи, не создавая циклов.

### `placeDoorBetween`

Получает пару комнат `(A, B)` и должен поставить «зеркальную» пару дверей: одна на стене A, вторая на противоположной стене B; обе связаны через `nextDoor` — это «портал», который переносит игрока между комнатами при движении.

Логика выбора оси (горизонтальная или вертикальная дверь): зависит от относительного положения центров. Сейчас в коде используются проверки `isInBetweenX/Y` — они работают, только если центр одной комнаты лежит **в проекции** другой по одной из осей. Это не покрывает диагональное расположение пар.

> ⚠️ **Известная проблема, см. раздел «Недостатки»:** при разнесённых комнатах `placeDoorBetween` молча выходит, не ставя двери, что приводит к бесконечной регенерации.

### Сложность

| | |
|---|---|
| Перечисление рёбер | O(n²) |
| Сортировка | O(n² log n) |
| Краскал с path-compression DSU | O(n² · α(n)) ≈ O(n²) |
| Установка дверей | O(n) |
| Итого | O(n² log n) |

Для `n=100` — несколько миллисекунд.

### Преимущества

- **Связное дерево гарантированно** — `n-1` ребро по построению.
- **Минимальная сумма расстояний** — ближайшие комнаты соединяются охотно, дальние только если иначе нельзя.
- **Без дублирующих рёбер** — каждая дверь имеет смысл.
- **Чистая структура подземелья** — навигация осмысленна, нет «проходного двора».

### Недостатки

- **`placeDoorBetween` пропускает диагональные пары** — корневая причина текущих проблем при больших world.
- **Двери — телепорты, без коридоров.** Между связанными комнатами нет физического прохода — `nextDoor` переносит игрока мгновенно. На малых world это незаметно, на больших — выглядит странно.
- **Нет «лишних» рёбер для loop'ов.** Чистое MST = одна тропа между любыми двумя комнатами. Канонический рогалик добавляет 15-25% случайных дополнительных рёбер для альтернативных путей; здесь этого нет.
- **`findToPlaceDoorX/Y` имеет затаённый баг** — `||` вместо `&&` в условии цикла; на текущих данных не срабатывает, но при `direction.x == 0` уйдёт в бесконечный цикл.

## 7. Этап 4 — Phase Four: стены через 4-битную маску

### Что делает

`PhaseFourCreateRoomStructure.applyWalls(room)`:

1. Находит все **edge-клетки** комнаты (по расширенному критерию: кардинальный null **или** диагональный null при двух смежных cells).
2. Для каждой edge-клетки вычисляет 4-битную маску — какие из её 4 кардинальных соседей сами edge.
3. По маске берёт глиф из `TilesUtils.WALL_TILES` и заменяет содержимое клетки на `Wall(glyph)`.
4. Двери (`Cell.getObject() instanceof Door`) пропускаются — Phase Three уже разместил их.

### Расчёт маски — иллюстрация

Возьмём прямоугольную комнату 5×4. Помечаем edge (E) и interior (·):

```
   x=0  1  2  3  4
y=0  E  E  E  E  E
y=1  E  ·  ·  ·  E
y=2  E  ·  ·  ·  E
y=3  E  E  E  E  E
```

Считаем маску для трёх типичных клеток:

```
(0, 0) — top-left угол:    (1, 0) — top edge:          (4, 0) — top-right:

   N=null (bit 0=0)            N=null (bit 0=0)             N=null (bit 0=0)
        ↑                            ↑                            ↑
        │                            │                            │
W=null ─C─ E:edge (bit 1=1)   W:E ─ C ─ E:E (bits 1,3)    W:E ─ C ─ E=null (bit 1=0)
        │                            │                            │
        ↓                            ↓                            ↓
   S=E (bit 2=1)               S=· interior (bit 2=0)      S=E (bit 2=1)

   маска WSEN = 0110 = 6        маска = 1010 = 10             маска = 1100 = 12
   глиф = ┌                     глиф = ─                       глиф = ┐
```

Результат — корректный замкнутый прямоугольник:

```
┌───┐
│   │
│   │
└───┘
```

| 0001 | 1  | ╵ | конец вверх |
| 0010 | 2  | ╶ | конец вправо |
| 0011 | 3  | └ | угол bottom-left |
| 0100 | 4  | ╷ | конец вниз |
| 0101 | 5  | │ | вертикаль |
| 0110 | 6  | ┌ | угол top-left |
| 0111 | 7  | ├ | T влево |
| 1000 | 8  | ╴ | конец влево |
| 1001 | 9  | ┘ | угол bottom-right |
| 1010 | 10 | ─ | горизонталь |
| 1011 | 11 | ┴ | T вверх |

| 1110 | 14 | ┬ | T вниз |
| 1111 | 15 | ┼ | крест |

### Вогнутые углы

Базовая маска (только по кардинальным null) **не покрывает** клетки в точках стыка T- и +-форм, где все 4 соседа — cells, но сама клетка является «внутренним углом». Расширенный критерий edge добавляет такие клетки через проверку диагональных null:

```
T-форма после слияния A (узкая верхняя) с B (широкая нижняя):

      x=5 6 7 8
y=0   ╭═════╮             ← узкая верхняя A
y=1   ║     ║
y=...
y=5   ║     ║
y=6   ╶─────╶─────────╴   ← (5,6) и (8,6) — вогнутые углы T-junction
y=...
y=9   ╰────────────────╯   ← широкая нижняя B
```

Без расширенного критерия (5,6) и (8,6) считались бы interior, и в их местах оставались бы «обрубки» стен — короткие висячие концы.

### Сложность

Пусть `c` — количество cells в комнате.

| | |
|---|---|
| Поиск edge-клеток | O(c) — один проход. |
| Подсчёт маски на каждой edge | O(1) — четыре lookup'а в `Set`. |
| Установка глифа | O(1) — lookup в `Map<Integer, Character>`. |
| Итого на одну комнату | O(c). |
| Итого на весь этаж | O(total_cells). |

Для типичной карты — миллисекунды.

### Преимущества

- **Один проход** вместо двух (раньше было: построить контур → второй пасс корректировки углов).
- **Никаких сравнений по символам** — логика опирается на топологию, а не на конкретный ассет. Смена стиля стен (`thin → heavy → double`) не требует правок Phase Four.
- **Полная классификация всех 16 случаев**, включая T-junction и крест.
- **Покрывает вогнутые углы** через расширенный критерий edge.
- **Расширяемо**: добавить новый стиль = добавить пары в `WALL_TILES`, ничего больше не трогать.

### Недостатки

- **Диагональные стыки без перекрытия** не лечатся — если две комнаты соединены только по углам диагональных cells (без общих cells), получаются ступенчатые «швы». В текущей форме генератора такие случаи редки, но возможны.
- **`MapDrawer.draw` дублирует** глиф во вторую колонку (дабл-широкая клетка): нужно класть `─` для продолжения, а не копию глифа угла. Это уже починено через `TilesUtils.continuesEast` + lookup горизонтали.
- **Зависимость от `AssetPool` на этапе class-init** в TilesUtils — хрупко. Если кто-то когда-нибудь дёрнет TilesUtils раньше AssetPool, упадёт NPE.

## 8. MapValidator — проверка связности

### Что проверяет

1. **Каждая комната имеет хотя бы одну дверь** — иначе она «висит в пустоте».
2. **Граф дверей связный** — из любой комнаты достижима любая другая.

### Алгоритм — BFS с visited

```java
visited = {start}
queue = [start]
while queue not empty:
    current = queue.poll()
    for door in current.doors:
        if door.nextDoor is null: return false   // висячая дверь
        neighbor = door.nextDoor.currentRoom
        if neighbor is null: return false         // битая дверь
        if visited.add(neighbor):                 // если новая
            queue.add(neighbor)

return visited.size() == rooms.size()
```

Канонический BFS, ничего хитрого. Линейный обход графа, каждая комната посещается ровно один раз.

### Сложность

| | |
|---|---|
| Время | O(V + E), где V — комнаты, E — двери. Для MST: O(n + (n-1)) = O(n). |
| Память | O(V) на visited. |

### Преимущества

- Корректный, общеизвестный паттерн.
- Ловит все три класса ошибок: висячие двери, битые двери (без `currentRoom`), несвязные подкомпоненты.
- Линейная сложность.

### Недостатки

- На текущей конфигурации (MST + 100 комнат) валидатор почти всегда возвращает true — он перестал быть «фильтром». Если хочется ловить и более тонкие дефекты (например, «эта дверь ведёт в стену»), нужно добавлять отдельные проверки.

## 9. Итоговая сложность

| Фаза | Время | Память |
|------|-------|--------|
| Phase One | O(n · c̄) | O(n · c̄) |
| Phase Two | O(n² · c̄) | O(n · c̄) |
| Phase Three | O(n² log n) | O(n²) |
| MapValidator | O(n) | O(n) |
| Phase Four | O(n · c̄) | O(n · c̄) |
| **Итого** | **O(n² log n + n² · c̄)** | **O(n · c̄)** |

где `n = roomCount`, `c̄` — среднее число cells в комнате.

В реальности на `n=100` cells комнат от 36 до 225 (`6×6 .. 15×15`). Сильнее всего грузит Phase Two (`hasIntersects` через `Set.retainAll`). Если переписать на AABB, доминанта станет Phase Three с сортировкой рёбер.

При этом каждое ребро MST лежит в очереди на размещение двери (через `placeDoorBetween`), и весь pipeline крутится в `Floor.regenerate` пока валидатор не пропустит карту. Если pipeline стабилен — обычно одной попытки хватает.

---

## 10. Преимущества решения в целом

1. **Чёткая декомпозиция на фазы.** Каждый класс — одна ответственность, фазы развязаны через промежуточный `Map<Integer, Room>`. Можно править одну фазу не трогая соседей.

2. **Generate-and-Test через `MapValidator`.** Грязная попытка отбрасывается, чистая идёт дальше — типичный roguelike-паттерн.

3. **Двойная система координат (локальная + lt).** Компактно (cells хранятся локально) и масштабируемо (комната может стоять в любой точке мира).

4. **MST вместо all-pairs.** Дерево из `n-1` ребра — навигационно осмысленное подземелье вместо «проходного двора».

5. **4-битная маска edge с расширением на вогнутые углы.** Покрывает все возможные топологии стен в один проход, без сравнений по символам ассетов.

6. **Двери как `Scriptable` объекты.** Реализация через `door.doAction(player)` элегантна — дверь телепортирует, лестница меняет этаж, рычаг открывает другую дверь, и всё через тот же интерфейс.

7. **Поддержка произвольных форм комнат.** L, T, +, ступенчатые — Phase Two может слить любые пересекающиеся прямоугольники, Phase Four нарисует контур.

8. **Воспроизводимость через seed.** При фиксированном `game.random.seed` карта генерируется одинаково при каждом запуске.

## 11. Недостатки и известные проблемы

### Критичные (блокируют работу)

- **`placeDoorBetween` пропускает диагональные пары комнат.** При больших world и редком расположении комнат `isInBetweenX/Y` ни на одной паре MST не возвращает true → дверей не ставится → валидатор отбраковывает → бесконечная регенерация. Фикс известен: выбирать ось по доминирующему `|dx| vs |dy|`.

### Серьёзные (ухудшают качество карт)

- **Двери = телепорты, без коридоров.** Между соединёнными комнатами на пустом мире нет физического перехода. Игрок исчезает в одной двери, появляется в другой. Канон: вырезать L-shaped или прямой коридор по cells между дверями.
- **Нет «лишних» рёбер для loop'ов.** Чистое MST даёт ровно одну тропу между парой комнат. Канон: добавлять 15-25% случайных дополнительных рёбер для альтернативных путей.

### Средние (баги, ждут срабатывания)

- **`findToPlaceDoorX/Y`**: `||` вместо `&&` в условии цикла. На текущих данных не срабатывает (выход через ранний return), но при `direction.x == 0` или `direction.y == 0` уйдёт в бесконечный цикл.
- **Cells после `combine` не копируют содержимое.** Объекты в исходных cells (например, `placeObject` в Phase One — цифра roomId, `*` в центре) теряются. Сейчас это не критично — отладочный мусор, — но если в комнатах появятся реальные объекты до Phase Two (предметы, существа, рычаги), их потеряет.
- **`Position` имеет Lombok `@Setter` (мутирующий)**, хотя по новому контракту `set()` возвращает новый объект. Кто-нибудь когда-нибудь напишет `pos.setX(5)` — и сломает HashMap-ключ.

### Косметические (не баги, но раздражают)

- **Отладочный мусор в Phase One и Phase Two**: цифра roomId в (1,1), `*` в центре, цифра кластера в (2,1). После Phase Four частично затирается, но `*` в центре остаётся. Должно быть за `debug.show.*`-флагом.
- **`Math.sqrt` в `Position.getDistance`** вместо squared distance для сравнений. Для `n=100` пар это `n²` извлечений корня — ничтожно, но архитектурно неаккуратно.
- **`hasIntersects` через `Set.retainAll`** вместо AABB-overlap — O(c) вместо O(1).

### Архитектурные

- **Нет коридоров вообще.** Это не баг, а отсутствующая фича. Без коридоров подземелье — это набор «телепортирующих кабинок».
- **Нет типов комнат.** Все одинаковые. Boss / treasure / start / exit — отсутствуют.
- **Нет интерьера комнат.** Cells внутри пустые — ни мебели, ни ловушек, ни обстановки.
- **Нет связи между этажами.** `Floor.regenerate` — это перегенерация **этого** этажа. Лестница вверх/вниз отсутствует.
- **Тестов нет.** При всей чистоте декомпозиции — pipeline идеально подходит для property-based тестов: «возвращённая карта валидна», «все cells лежат в bounds», «граф дверей связный», но это не реализовано.

## 12. Объективная оценка

### Что хорошо

Алгоритм **архитектурно зрелый**. Декомпозиция на фазы, валидатор как Generate-and-Test gate, двухкоординатная модель, MST вместо all-pairs, 4-битная маска вместо 5 if-цепочек — всё это правильные инженерные решения, а не «лишь бы работало». Большинство фаз выглядят канонически и понятно.

Особенно сильные места:
1. **MST** + **DSU** в Phase Three: учебный пример Краскала, чисто реализовано.
2. **4-битная маска** в Phase Four: переход от хрупких сравнений по символам к топологической классификации — это качественный архитектурный скачок.
3. **BFS-валидатор**: после фикса работает корректно, ловит все классы ошибок графа дверей.

### Что плохо

**Текущее состояние не production-ready** из-за бага в `placeDoorBetween` — пользователь это уже видит на больших world'ах. Один локализованный фикс (выбор оси по `|dx| vs |dy|`) уберёт бесконечную регенерацию, но это, что называется, «низко висящий фрукт» — баг очевидный и копеечный.

**Отсутствие коридоров** — ключевое архитектурное упущение. Подземелье без коридоров чувствуется как набор изолированных «комнат с порталами», а не как связное пространство. Это ставит весь визуальный полировка (стили рамок, Catppuccin палитра, сглаженные углы) в неловкое положение — фундамент пробит.

**Хвост мелких багов** (`||` vs `&&`, мутабельный `Position`, потеря cells при `combine`, отладочный мусор) — каждый по отдельности тривиален, но в совокупности они «прыгают» наружу, когда меняешь параметры или пишешь новый код. Это техдолг.

### Чего не хватает для уровня хороших рогаликов

| | Ваш генератор | NetHack / DCSS / Brogue |
|---|---|---|
| Связное дерево комнат | ✓ | ✓ |
| MST + лишние loops | частично (только MST) | ✓ |
| Коридоры | ✗ | ✓ |
| Типы комнат (start/exit/boss/etc) | ✗ | ✓ |
| Интерьер | ✗ | ✓ |
| Лестницы между этажами | ✗ | ✓ |
| Воспроизводимость по seed | ✓ | ✓ |
| Property-based тесты | ✗ | частично |

### Если расставлять приоритеты

**P0** — починить `placeDoorBetween` (выбор оси по `|dx| vs |dy|`). Без этого ничего не работает на больших world'ах. ~30 строк изменений.

**P1** — реализовать коридоры. Это самое заметное архитектурное улучшение. Без них всё дальнейшее (типы комнат, интерьер) играется «в пустоте». Существенный объём, но изолированный — Phase Three после MST вырезает коридоры по cells между дверями, Phase Four видит их как edge-клетки и красит как обычные стены.

**P2** — добавить лишние рёбра поверх MST (15% от размера). Несколько строк, ощутимое улучшение навигации.

**P3** — типы комнат и интерьер. После того как костяк генератора стабилен.

**P4** — property-based тесты на генератор. При текущей чистой структуре — буквально 5-6 инвариантов покрывают 80% возможных регрессий.

### Итоговая оценка по 10-балльной шкале

- **Архитектура и декомпозиция: 9/10.** Очень хорошо. Минус один — за отсутствие тестов.
- **Корректность отдельных фаз: 7/10.** После всех фиксов в этой ветке — большинство фаз работают корректно. Минус — за оставшийся баг в `placeDoorBetween` и хвост мелочей.
- **Производительность: 8/10.** На целевых масштабах (`n ≤ 100`) — миллисекунды на этаж. Замена `hasIntersects` на AABB добавит, но и без того нормально.
- **Качество результирующих карт: 5/10.** Без коридоров и типов комнат — карта функциональна, но не «играется». Это самое слабое место.
- **Расширяемость: 8/10.** Каждая фаза изолирована, контракты простые, новые фичи накладываются естественно.

**Среднее: 7.4 / 10.** Хорошая база с одной критичной починкой и несколькими крупными фичами впереди. С реализованными коридорами + лишними рёбрами + типами комнат уверенно вытянул бы на 9.
